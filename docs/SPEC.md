# 반도체 Fab 설비 배치 최적화 시뮬레이터 — 상세 설계서

버전: 0.3 (M1·M2 구현 반영)
최종 수정: 2026-07-27

> **M1 구현 중 두 곳이 수정되었다.** 아래 본문은 아직 원안이며, 실제 구현과 다른 부분이
> 있다. 정확한 현행 사양은 코드와 그 docstring이 기준이다.
>
> 1. **§5.1 기하 — 수정됨.** bay 내부 slot이 spine과 평행하게 늘어서도록 적혀 있었으나,
>    실제 spine/bay 레이아웃에서 bay는 spine에 **수직**이다(§4.3의 "slot 0이 입구
>    최근접"과도 모순). 수직 bay + 중앙 통로 **양벽 배치**로 구현했다.
>    slot = `(bay, 좌/우, 위치)`, 기본 기하는 5 bay × 2벽 × 3위치 = **30 slot**
>    (설계서의 6 bay × 6 slot = 36에서 변경).
> 2. **§5.3 반송 — 요소 추가.** 실제 AMHS는 intrabay/interbay가 분리되어 있어 bay를
>    넘는 lot은 **스토커 입출고**를 거친다(항방향 120초). 이 요소를 빼면 반송 부하가
>    처리시간의 1.8%뿐이고 그중 71%가 배치와 무관한 고정시간이라, **배치가 처리량에
>    영향을 주지 못한다**(반송차 가동률 21%). 추가하면 6.0% / 67%가 되어 민감 구간에
>    들어온다. §12의 범위 외 항목 중 "스토커"는 **재고 보관만** 범위 외이고,
>    경계 통과 비용은 범위 내로 옮겼다.
>
> 이에 따라 §7.2 대리지표는 흐름-거리만이 아니라 **bay 교차 횟수**를 주항으로 담아야
> 한다 — 스토커 항이 반송 부하의 지배항이기 때문이다.
>
> **M2 구현 중 §7.3 계산량 추정이 틀린 것으로 확인됐다.**
>
> 3. **§7.3 — 이벤트 수를 약 18배 과대추정했다.** "스텝당 이벤트 5개"를 가정해 실행
>    1회를 84만 이벤트 / 1.7초로 잡았으나, 실제 구현은 **스텝당 이벤트 1개**다
>    (큐 진입과 착수를 이벤트가 아니라 함수 호출로 처리). 실측은 실행 1회 약 4.6만
>    이벤트 / 0.16초이며, 후보 20개 검증이 12분 대신 **1분 미만**이다.
>    초당 이벤트 수 자체는 약 35만으로 목표(50만)의 70%지만, 목표치가 잘못된 이벤트 수
>    추정에서 나온 값이므로 판단 기준은 절대 실행시간이다. 그 기준으로는 제약이 아니고,
>    M6에서 후보 수(K)와 반복 횟수를 오히려 늘릴 여유가 있다. 단 M3에서 고장·배치·반송
>    이벤트가 붙으면 스텝당 2~3개로 늘어나므로 그때 재측정한다.
> 4. **`analytic_capacity(batching=)` 추가.** 배치 형성이 없는 M2 엔진과 해석적 상한을
>    같은 전제로 비교하기 위한 스위치다. 전제가 다르면 "DES 실측 ≤ 해석적 상한"이라는
>    정합성 검증이 성립하지 않는다.
> 5. **첫 lot 투입 시각 = 0.** 첫 간격만큼 뒤로 미루면 모든 결과가 평행이동한다
>    (SimPy 교차검증에서 발견).

## 0. 이 문서의 목적

인터뷰로 확정한 요구사항을 구현 가능한 수준까지 내려쓴 설계서다. 구현 착수 전 검토용이며,
"왜 이렇게 정했는지"와 "무엇이 아직 위험한지"를 함께 적었다. 반도체 공정 도메인 용어는
처음 등장할 때 설명을 붙였다.

구현은 이 문서에 대한 승인 후 시작한다.

## 1. 인터뷰 확정 사항

| 항목 | 결정 | 비고 |

| 공간 모델 | Bay 구조 (실제 fab 방식) | 중앙 spine 통로 + 양측 bay |
| 산출물 | 코어 라이브러리 + 웹 UI | Python 라이브러리 → FastAPI → 정적 HTML/JS |
| 공정 흐름 데이터 | 벤치마크(SMT2020/MIMAC) 구조를 닮은 축소 내장 데이터셋 + 원본 로더 | 원본은 이 환경에서 다운로드 불가 (§4.1) |
| 반송 모델 | 반송기 대수를 제한한 공유 자원 모델 | 상세 궤도 점유는 제외 |
| 현실성 요소 | 재진입 흐름, 설비 고장(MTBF/MTTR), 배치 설비 | 셋업 체인지는 범위 외 (§12) |
| 최적화 엔진 | 2단 구조: 거리 대리지표 스크리닝 → DES 검증 | §7 |
| 디스패칭 | FIFO 기본 + 규칙 교체 가능한 플러그인 지점 | §6.6 |
| 결정 변수 | 설비→bay 배정 + bay 내 위치 + 반송기 대수 + 설비 대수 | 예산 제약 필수 (§7.1, §11-A) |
| 투입 정책 | 병목 포화까지 밀어서 최대 생산능력 산정 | 능력 탐색 루프 필요 (§6.8) |
| Before 기준선 | 실무 관행 배치(동종 설비를 한 bay에 = 기능별 배치) | §8 |
| 웹 UI 시각화 | 2D 배치도, 지표 대시보드, Before/After 비교, 웨이퍼 이동 애니메이션 | §10 |

## 2. 도메인 모델과 용어

### 2.1 물리 계층

```
                        ┌──────────┐┌──────────┐┌──────────┐
                        │  BAY 1   ││  BAY 2   ││  BAY 3   │   ← 북측 bay
                        │ □□□□□□   ││ □□□□□□   ││ □□□□□□   │      (slot 6개씩)
                        └────╥─────┘└────╥─────┘└────╥─────┘
   ═══════════════════════════╬═══════════╬═══════════╬═══════════════  ← SPINE (간선 통로)
                        ┌────╢─────┐┌────╢─────┐┌────╢─────┐
                        │ □□□□□□   ││ □□□□□□   ││ □□□□□□   │
                        │  BAY 4   ││  BAY 5   ││  BAY 6   │   ← 남측 bay
                        └──────────┘└──────────┘└──────────┘
                             ╥ = bay 입구(spine 접속점),  □ = slot(설비 1대 자리)
```

- **Bay**: 클린룸을 구획한 단위 공간. 실제 fab에서는 중앙 간선 통로(spine)에 빗살처럼 붙는다.
- **Slot**: bay 내부의 설비 1대 자리. 이 모델에서는 등간격 이산 위치로 단순화한다.
- **Spine**: bay들을 잇는 간선 통로. 모든 bay 간 이동은 spine을 경유한다.
- **Bay 입구(portal)**: bay와 spine의 접속점. bay 내 이동 거리는 이 지점 기준으로 계산한다.

### 2.2 논리 계층

- **Lot(롯)**: 웨이퍼 25장을 담은 운반 단위. **시뮬레이션의 최소 이동/처리 단위는 lot이다**
  (웨이퍼 단위로 하면 계산량이 25배가 되고, 실제 fab도 lot 단위로 반송한다).
- **Tool(설비)**: 개별 장비 1대. 반드시 하나의 slot을 점유한다.
- **Tool group(설비 그룹)**: 동일 공정을 수행하는 대체 가능한 설비들의 집합
  (예: 스캐너 3대 = PHOTO 그룹). 라우트는 그룹을 지정하고, 실제 배정은 디스패처가 한다.
- **Route(라우트)**: 제품 하나가 거치는 공정 단계(step)의 순서 목록.
- **Step**: `(순번, 설비그룹, 처리시간)`. 라우트에는 같은 그룹이 여러 번 등장한다.
- **재진입(re-entrant) 흐름**: 반도체 특유의 성질. 웨이퍼는 층(layer)을 하나씩 쌓으므로
  같은 노광/식각 설비를 레이어마다 다시 방문한다. 내장 데이터셋에서 PHOTO 그룹은 한 제품당
  10회 재방문한다. 배치 최적화 관점에서 핵심 요소다 — 방문 빈도가 높은 그룹의 위치가
  이동거리 총합을 지배한다.
- **배치 설비(batch tool)**: 확산로·세정 장비처럼 여러 lot을 모아 한 번에 처리하는 설비.
  lot을 모으는 대기시간이 발생한다.
- **MTBF / MTTR**: 평균 고장간격 / 평균 수리시간. 가동률 A = MTBF / (MTBF + MTTR).
- **AMHS / OHT**: 자동 물류 시스템 / 천장 궤도 반송차. 이 모델에서는 "대수가 제한된
  공유 자원"으로 추상화한다.
- **X-factor**: 실제 사이클타임 ÷ 순수 처리시간 합. 대기시간이 얼마나 붙었는지를 나타내는
  실무 표준 지표. 양산 fab은 통상 2~4.

## 4. 데이터

### 4.1 벤치마크 원본을 쓰지 못하는 이유

- **SMT2020**: Kopp, Hassoun, Kalir, Mönch (2020), *SMT2020 — A Semiconductor Manufacturing
  Testbed*, IEEE Trans. on Semiconductor Manufacturing. HVLM(대량·소품종)과 LVHM(소량·다품종)
  두 fab 모델로 구성되며, 설비 1,000대 이상 / 라우트 수백 스텝 / 배치·셋업·MTBF·작업자
  데이터를 포함한다.
- **MIMAC**: SEMATECH(1997) testbed 데이터셋. 설비 그룹 80~100여 개 규모.

두 가지 문제가 있다.

1. **접근 불가**: 이 실행 환경의 네트워크 정책이 배포처를 차단한다 (확인된 403).
2. **규모 불일치**: 원본은 설비 1,000대급인데 확정된 범위는 10~40대다. 그대로 쓸 수 없고
   어차피 축소가 필요하다.

따라서 **구조는 벤치마크를 따르고 규모만 축소한 내장 데이터셋**을 리포지토리에 동봉하고,
원본 파일을 나중에 넣으면 읽는 로더를 별도로 구현한다. 로더는 원본 스키마 기준으로
작성하되, 실제 파일로 검증하지 못한 상태임을 코드와 문서에 명시한다.

> **중요**: 내장 데이터셋의 수치는 벤치마크 원본 값이 아니다. "벤치마크와 같은 구조·같은

> 이 구분을 반드시 표시해야 한다.

## 5. 거리 / 경로 모델

### 5.1 좌표

Bay `b`의 slot `s` 중심 좌표:

```
bay_index_in_row = (b - 1) mod 3
x(b, s) = bay_index_in_row × (slots_per_bay × slot_pitch + bay_gap) + (s + 0.5) × slot_pitch
y(b, s) = + (spine_width/2 + bay_depth/2)   (북측 bay)
          - (spine_width/2 + bay_depth/2)   (남측 bay)
```

Bay 입구(portal): `x_portal(b) = bay 중앙의 x`, `y_portal(b) = ±spine_width/2`

### 5.2 이동 거리

Slot A(bay `b1`) → Slot B(bay `b2`):

- **같은 bay**: `|x_A − x_B|` (bay 내부 통로 직선 이동)
- **다른 bay**: `|x_A − x_portal(b1)| + |y_A − y_portal(b1)|`
              `+ |x_portal(b1) − x_portal(b2)|` (spine 구간)
              `+ |x_portal(b2) − x_B| + |y_portal(b2) − y_B|`

전부 맨해튼 거리다. 궤도는 직교 격자이므로 유클리드보다 맨해튼이 맞다.

거리 행렬 `D[36][36]`은 레이아웃 기하가 정해지면 한 번 계산해 캐시한다.
**레이아웃 기하가 결정 변수가 아니므로 최적화 전체에서 이 행렬은 불변이다** — 배치를 바꿔도
거리 행렬은 그대로이고 "어느 설비가 어느 slot에 있는지"만 바뀐다. 대리지표 평가가
빠른 이유가 이것이다.

### 5.3 이동 시간

```
travel_time = distance / speed_mps
total_move_time = load_time + travel_time + unload_time + 2 × handoff_time
```

빈차 이동(직전 하차 지점 → 다음 상차 지점)도 같은 식으로 계산해 반송기 점유에 포함한다.

### 5.4 배치가 실제로 처리량에 영향을 주는 경로 — 설계상 가장 중요한 점

기본 데이터셋에서 처리시간은 20~240분인데 이동시간은 30~120초다. **이동시간을 사이클타임에
그냥 더하는 것만으로는 배치의 영향이 1~3%밖에 안 나온다.** 배치가 의미를 갖는 실제 경로는
다음이다.

```
배치 개선 → 평균 이동거리 ↓ → 반송기 1대당 작업량 ↓ → 반송기 가동률 ↓
         → 반송 대기(큐) 시간 ↓↓ → 설비 유휴 감소 → 처리량 ↑
```

반송기 대수가 여유롭다면 이 경로가 끊기고 배치는 사실상 무의미해진다. 따라서
**반송기 대수를 민감한 구간에 두는 것이 시나리오 설계의 핵심**이다.

기본값 검산: lot당 이동 84회, 6.4 lot/일 → 538 이동/일. 평균 이동 소요(빈차 포함) 약 200초
→ 총 107,600초/일. 반송기 1대의 하루 가용시간 86,400초.

- 반송기 1대 → 요구 125% → **포화, 반송이 병목**
- 반송기 2대 → 가동률 약 62% → **민감 구간 (기본값)**
- 반송기 4대 → 가동률 약 31% → 배치 영향 거의 소멸

시나리오 검증 시 반송기 가동률이 55~85% 밖으로 나가면 경고를 띄운다.

## 6. DES 엔진

### 6.1 이벤트 루프

`heapq` 기반 최소 힙. 이벤트는 `(time, seq, kind, payload)` 튜플.

```
kinds: LOT_RELEASE, MOVE_REQUEST, VEHICLE_ASSIGNED, MOVE_ARRIVE,
       PROC_START, PROC_END, TOOL_DOWN, TOOL_UP, BATCH_TIMEOUT, LOT_DONE
```

`seq`는 동시각 이벤트의 결정론적 순서를 보장하는 단조 증가 카운터 — 같은 seed면 항상
같은 결과가 나와야 한다(재현성).

난수는 스트림별로 분리한다: 처리시간 / 고장 / 수리 / 투입. 공용 스트림 하나를 쓰면 배치를
바꿨을 때 난수 소비 순서가 달라져 "배치 효과"와 "난수 노이즈"가 섞인다. **공통 난수(CRN)
분리는 배치 비교의 신뢰성에 직결된다.**

### 6.2 Lot 생애주기

```
투입 → [스텝 반복: 반송 요청 → 반송기 배정 → 이동 → 도착 → 큐 진입
        → (배치설비면 배치 형성 대기) → 설비 점유 → 처리 → 완료] → 출하
```

### 6.3 설비 상태

`IDLE / BUSY / DOWN / BLOCKED`. 처리 중 고장이 나면 **처리를 중단하고 수리 후 재개**한다
(잔여시간 보존). 처리 중 폐기(scrap) 모델은 범위 외.

### 6.4 고장 모델

- 고장간격: 지수분포 `Exp(1/MTBF)`, **가동시간(busy time) 기준**으로 카운트
  (달력시간 기준으로 하면 유휴 설비도 고장나 가동률 계산이 왜곡된다)
- 수리시간: 로그정규 `mean=MTTR, CV=0.4`

### 6.5 배치 설비

배치 형성 정책 `greedy_full`:

1. 큐에 같은 그룹 lot이 `batch_size`개 모이면 즉시 착수
2. 부족한 상태로 `max_wait`(기본 60분) 경과 시 부분 배치로 착수
3. 서로 다른 제품의 lot은 같은 배치에 섞을 수 있다 (동일 그룹 = 동일 레시피 가정)

부분 배치 착수는 반드시 필요하다 — 순수 full-batch만 허용하면 저부하 구간에서 lot이 영구
대기할 수 있다.

### 6.6 디스패칭 (플러그인)

```python
class DispatchRule(Protocol):
    def select(self, queue: list[Lot], tool: Tool, now: float) -> Lot | None: ...
```

기본은 `fifo`. `srpt`(최소잔여작업), `edd`(납기순), `cr`(임계비)은 인터페이스 자리만 만들고
구현은 후속. 그룹별로 다른 규칙을 지정할 수 있게 한다.

### 6.7 반송

- 반송기 `N`대를 공유 자원 풀로 관리. 각 반송기는 현재 위치(slot 또는 이동 중)를 갖는다.
- 이동 요청이 오면 **유휴 반송기 중 빈차 이동거리가 가장 짧은 것**을 배정 (nearest-vehicle)
- 유휴 반송기가 없으면 FIFO 요청 큐에 대기
- 반송 대기시간을 지표로 별도 집계한다 (배치 효과의 주 경로이므로)

궤도 구간 점유·추월·정체는 모델링하지 않는다 (인터뷰 확정 사항).

### 6.8 생산능력 탐색 (`capacity_search`)

"병목 포화까지 밀어서 최대 생산량 산정"을 구현하는 절차다. 투입률을 올리다 보면 어느
지점부터 **생산량은 더 늘지 않고 WIP와 사이클타임만 폭발**한다. 그 직전 지점을 찾는다.

```
1. 해석적 상한 R_max 계산 (§4.2 방식). 순수 계산, DES 불필요.
2. 조대 램프(coarse ramp): R = 0.70, 0.80, 0.88, 0.94 × R_max 로 DES 실행.
   각 실행에서 판정:
     - WIP 안정성: 후반 50% 구간에서 WIP 선형 회귀 기울기 ≈ 0 이어야 함
       (기울기가 양수면 WIP 발산 = 포화 초과)
     - 사이클타임 ≤ cycle_time_cap_h
   두 조건을 만족하는 최대 R 을 R_lo, 최초 실패 R 을 R_hi 로 확정.
3. 이분 탐색: [R_lo, R_hi] 구간을 3회 이분 → 정밀도 약 R_max의 1%.
4. 결과: 달성 생산량(lot/일, 웨이퍼/일), 그 지점의 사이클타임·WIP·가동률.
```

DES 실행 횟수 = 램프 4회 + 이분 3회 = **후보 1개당 7회** (× replications 3 = 21회).
이것이 최적화 계산량의 지배 항이다 (§7.3).

**최적화 목표함수**는 이 절차의 산출인 `capacity(후보)` = 달성 생산량(웨이퍼/일)이다.

### 6.9 워밍업과 통계

- 워밍업 30일 구간의 통계는 버린다 (초기 WIP=0 상태의 낙관 편향 제거)
- 워밍업 이후 90일 집계. 독립 시드 3회 반복 후 평균 + 95% 신뢰구간
- 신뢰구간 폭이 평균의 5%를 넘으면 반복 횟수 부족을 경고

## 7. 최적화 엔진

### 7.1 결정 변수와 제약

**결정 변수**

| 변수 | 타입 | 범위 |
|---|---|---|
| `assignment[tool_instance]` | (bay, slot) | 겹침 없이 36 slot 중 하나 |
| `tool_count[group]` | 정수 | 그룹별 `[min, max]` (기본 min=1, max=6) |
| `vehicles` | 정수 | `[1, 8]` |

**제약**

1. **Slot 배타**: 한 slot에 설비 1대
2. **용량**: 총 설비 대수 ≤ 총 slot 수(36)
3. **capex 예산**: `Σ cost[g] × count[g] + cost[VEHICLE] × vehicles ≤ capex_limit` ← **필수**
4. **사이클타임 상한**: `cycle_time ≤ cycle_time_cap_h` (능력 판정에 이미 포함)
5. (선택) bay별 그룹 혼합 제약 — 실제 fab은 배관·용수·진동 요건으로 특정 그룹을
   특정 bay에만 둘 수 있다. `allowed_bays[group]` 로 표현 가능하게 하고 기본은 무제약.

> **왜 예산 제약이 필수인가**: 설비 대수를 변수로 두고 생산량을 최대화하면 답은 항상
> "모든 설비를 최대로 산다"가 된다. 배치 최적화 부분은 아무 영향도 없어지고 최적화가
> 무의미해진다. 예산 제약이 있어야 "같은 돈으로 배치를 잘해서 더 뽑는다"는 원래 질문이
> 성립한다. 기본 예산은 baseline 구성의 capex와 동일하게 설정해
> **"돈을 더 쓰지 않고 얼마나 개선되는가"**를 기본 실험으로 삼는다.

### 7.2 대리지표 (Stage 1)

DES 없이 계산하는 빠른 점수. 두 항의 가중합.

**(a) 흐름-거리 지표** — 배치 품질

```
F = Σ_{제품 p} mix_p × Σ_{연속 스텝쌍 (i,i+1)} E[ d(slot of group_i, slot of group_{i+1}) ]
```

같은 그룹에 설비가 여러 대이므로 정확한 목적지는 디스패칭에 달려 있다. 대리지표에서는
**그룹 내 설비 위치의 평균**을 사용한다 (기대 거리 근사).

**(b) 해석적 부하 지표** — 대수 구성 품질

```
U = max_g (요구작업량_g / (count_g × 1440 × A_g))          최대 그룹 가동률
V = 반송 요구작업량(F 기반) / (vehicles × 86400)           반송기 가동률
```

**결합 점수** (낮을수록 좋음)

```
score = w_F × normalize(F) + w_U × penalty(U) + w_V × penalty(V) + budget_penalty
penalty(x) = 1/(1−x) 형태 (포화에 가까울수록 급격히 나빠짐 — 대기행렬 이론의 형태를 모방)
```

가중치 기본값 `w_F=1.0, w_U=2.0, w_V=1.5`는 §13의 상관 검증으로 조정한다.

**대리지표의 한계를 명시한다**: 배치·고장·디스패칭의 상호작용을 담지 못한다. 그래서
스크리닝 전용이며 최종 판정은 반드시 DES가 한다.

### 7.3 2단 파이프라인

```
Stage 1: SA로 대리지표 최적화
  - 반복 200,000회 (후보 1개 평가 ≈ 50 µs → 약 10초)
  - 다양성 유지: 방문한 상위 해를 유사도 기준으로 걸러 저장
  - 산출: 서로 다른 상위 후보 K개 (기본 K=20)

Stage 2: DES 검증
  - 후보 K개 각각에 대해 §6.8 생산능력 탐색 (후보당 DES 21회)
  - 총 DES 실행 = 20 × 21 = 420회
  - 프로세스 병렬 (multiprocessing, 코어 수만큼)
  - 산출: 실제 생산량 기준 순위

Stage 3 (선택): DES 국소 개선
  - Stage 2 1위 해에서 이웃 20개를 DES로 직접 평가, 개선되면 이동. 5라운드.
```

**계산량 추정**: DES 1회 ≈ lot 2,000개 × 84스텝 × 이벤트 5개 ≈ 84만 이벤트.
자체 엔진 목표 성능 50만 이벤트/초 → **DES 1회 ≈ 1.7초**.
Stage 2 = 420 × 1.7초 ≈ 12분 (단일 코어), 8코어 병렬 시 **약 1.5분**.
Stage 3 포함 총 5분 내외. 웹 UI에서 진행률을 보여주며 기다릴 수 있는 수준이다.

이 추정이 2~3배 틀려도 감당 가능하지만, 10배 틀리면 K와 replications를 줄여야 한다.
**엔진 성능 측정은 구현 1단계의 첫 검증 항목이다** (§13).

### 7.4 이웃 연산자

| 연산자 | 내용 | 확률 |
|---|---|---|
| `swap_slots` | 두 설비의 위치 교환 | 0.35 |
| `move_to_empty` | 설비 하나를 빈 slot으로 이동 | 0.25 |
| `relocate_group` | 그룹 전체를 다른 bay로 이동 | 0.15 |
| `add_tool` | 그룹 설비 +1 (예산 내) | 0.08 |
| `remove_tool` | 그룹 설비 −1 | 0.07 |
| `change_vehicles` | 반송기 ±1 | 0.10 |

`relocate_group`이 중요하다 — 개별 설비를 한 칸씩 옮기는 것만으로는 "동종 설비를 모으거나
흩뿌리는" 구조적 변화에 도달하기 어렵다.

`add_tool`/`remove_tool`은 예산 제약을 깨면 다른 그룹을 줄여 예산을 맞추는 **복구(repair)**
루틴을 통과시킨다.

### 7.5 SA 파라미터

- 초기 온도: 무작위 이웃 100개의 점수 표준편차 × 2 (자동 결정)
- 냉각: 기하 냉각 `T ← 0.9995 T`
- 재가열: 20,000회 개선 없으면 초기 온도의 30%로 재가열

## 8. 기준선 (Before)

`baseline.py`가 **기능별 배치(functional layout)**를 생성한다 — 실제 fab의 표준 관행이며,
동종 설비를 같은 bay에 모으는 방식이다.

```
1. 그룹을 총 요구작업량(방문횟수 × 처리시간) 내림차순 정렬
2. 순서대로 bay에 할당. 한 그룹의 설비는 모두 같은 bay에, 같은 bay 안에서 slot 0부터 채움
3. bay 용량(6 slot)이 부족하면 다음 bay로 넘어감. 작은 그룹들은 남는 자리에 합침
4. 방문 빈도가 높은 그룹을 spine 중앙 쪽 bay(2번, 5번)에 우선 배치
   — 이건 실무자의 상식이므로 기준선에 포함해야 공정한 비교가 된다
```

`--baseline random` 옵션으로 무작위 배치도 생성 가능(새니티 체크용)이지만, 기본 비교
대상은 기능별 배치다. **무작위를 이기는 것은 성과가 아니다.**

사용자 지정 배치를 파일로 넣어 기준선으로 쓰는 것도 지원한다 (`assignment` 필드).

## 9. 지표

| 지표 | 정의 | 단위 |
|---|---|---|
| Throughput | 워밍업 이후 출하 lot 수 / 기간 | lot/일, 웨이퍼/일 |
| Cycle time | 투입 → 출하 경과시간 | 시간 (평균, 중앙값, p95) |
| X-factor | 사이클타임 / 순수 처리시간 합 | 배수 |
| Tool utilization | 처리시간 / (달력시간 − 고장시간) | 그룹별 % |
| Tool availability | 가동가능시간 / 달력시간 | 그룹별 % |
| Queue time | 그룹별 큐 대기시간 | 시간 (합계, 평균) |
| Transport wait | 반송기 배정 대기시간 | 시간 (합계, 평균) |
| Vehicle utilization | 반송기 작업시간 / 가용시간 | % |
| WIP | 시각별 재공 lot 수 | 개 (평균, 최대, 시계열) |
| Total travel | 총 이동거리 | km |
| Capex | Σ 단가 × 대수 | 상대 단위 |

**병목 진단 출력**: 가동률 상위 3개 그룹 + 큐 대기시간 상위 3개 그룹 + 반송 대기 비중.
"어디를 손대야 하는가"를 바로 알 수 있어야 한다.

### 10.3 애니메이션 이벤트 로그

전체 실행을 기록하면 이벤트가 수백만 개다. 다음으로 제한한다.

- 트레이스는 **명시적으로 켤 때만** 기록 (`trace: {enabled: true, window_h: [720, 744]}`)
- 기본은 워밍업 직후 24시간 구간만
- 형식: 컬럼 지향 JSON (필드별 배열) — 행 지향 대비 3~4배 작다

```json
{
  "t":        [720.0, 720.02, 720.5],
  "kind":     [1, 2, 3],
  "lot":      [104, 104, 104],
  "from":     [7, 7, 13],
  "to":       [13, 13, 13],
  "dur":      [0.02, 0.48, 1.0]
}
```

`kind`는 정수 코드(1=이동시작, 2=도착, 3=처리시작, 4=처리종료, 5=고장, 6=복구).

## 11. 열린 질문 (구현 착수 전 확인 필요)

### A. capex 단가표 — 답변 필요

§4.4의 단가는 상대적 순서만 반영한 자리표시자다. 실제 값을 아신다면 교체해야 하고,
모르면 자리표시자로 진행한다 (최적화 결과의 절대적 타당성은 이 표에 달려 있다).
기본 예산은 baseline capex와 동일하게 잡아 "추가 투자 없이 배치만으로 얼마나 개선되는가"를
기본 실험으로 둘 계획이다.

### B. 설비 대수 변경의 물리적 의미

설비를 늘리면 slot을 더 차지한다(모델에 반영됨). 하지만 실제로는 유틸리티(용수·가스·배기)
증설도 필요하다. 이 부분은 모델링하지 않고 capex 단가에 암묵적으로 포함된 것으로 본다.

### C. 납기 개념

`edd`/`cr` 디스패칭 규칙은 lot마다 납기가 있어야 의미가 있다. 현재 데이터셋에는 납기가
없다. 규칙 인터페이스만 만들고 실제 구현은 납기 모델 추가 시로 미룬다.

### D. 결과 발표 시 데이터 출처 표기

내장 데이터셋은 벤치마크 원본이 아니다(§4.1). 대외 자료에 쓸 경우 "SMT2020/MIMAC 구조를
참조한 합성 데이터"로 표기해야 한다.

## 13. 검증 계획

### 13.1 단위 테스트

| 대상 | 검증 내용 |
|---|---|
| `geometry` | 좌표 계산, 대칭성 (bay 1↔4 거리 = bay 3↔6 거리) |
| `distance` | 삼각부등식, 자기거리 0, 대칭성, 손계산 예제 3건 |
| `engine` | 이벤트 순서, 동시각 결정론성, 같은 seed → 같은 결과 |
| `station` | 단일 설비 M/M/1 근사와 대기시간 비교 (고장·배치 끄고) |
| `breakdown` | 장기 실행 시 실측 가동률 → 이론값 A=MTBF/(MTBF+MTTR) 수렴 (오차 1% 내) |
| `batching` | 배치 크기 준수, 부분 배치 타임아웃 동작, lot 영구대기 없음 |
| `transport` | 반송기 1대 시 이동시간 총합 = 가동시간, nearest-vehicle 선택 정확성 |
| `capacity` | 해석적 상한 ≥ DES 실측 능력 (반드시 성립해야 함) |
| `encoding` | 이웃 연산 후에도 제약 만족(slot 배타·예산), 복구 루틴 정확성 |
| `cost` | 예산 계산, 초과 판정 |

### 13.2 통합 검증

1. **엔진 성능 측정** ← 최우선. 목표 50만 이벤트/초. 미달 시 §7.3의 K·replications 재조정.
2. **SimPy 교차검증**: 설비 3대 / 스텝 5개 소형 모델을 SimPy로 별도 작성해 사이클타임·
   처리량이 5% 내로 일치하는지 확인. 자체 엔진의 논리 오류를 잡는 가장 확실한 방법.
3. **해석적 정합성**: `smallfab-21`을 저부하(투입률 = 상한의 50%)로 돌렸을 때
   사이클타임 → 순수 처리시간 합에 수렴하는지 (X-factor → 1.0~1.3).
4. **포화 거동**: 투입률을 상한 초과로 올렸을 때 WIP가 선형 발산하는지.
5. **대리지표 상관**: 무작위 후보 100개의 대리지표 점수 vs DES 실측 생산량의
   Spearman 순위상관. **목표 |ρ| ≥ 0.7**. 미달이면 §7.2 가중치를 재조정하거나
   대리지표 자체를 재설계한다 — 상관이 낮으면 2단 구조가 성립하지 않는다.
6. **최적화 유효성**: 최적화 결과가 기능별 배치 기준선보다 통계적으로 유의하게
   나은지 (반복 3회 신뢰구간 비겹침).
7. **재현성**: 같은 시나리오 + 같은 seed → 비트 단위 동일 결과.

### 13.3 성공 기준

- 기준선(기능별 배치) 대비 **동일 capex에서 생산량 개선** — 배치만으로는 개선 폭이
  작을 수 있다(§5.4). 개선이 1% 미만이라면 그것도 유효한 결론이며, "이 fab에서는
  배치보다 대수 구성이 지배적"이라고 보고한다. 억지로 큰 숫자를 만들지 않는다.
- 대리지표 상관 ρ ≥ 0.7
- 최적화 전체 실행 5분 이내 (8코어 기준)
- 모든 지표에 신뢰구간 동반

## 14. 구현 단계

| 단계 | 내용 | 산출물 | 검증 |
|---|---|---|---|
| **M1** | `core` + `data/builtin` + 거리 행렬 | 모델·기하·내장 데이터셋 | 13.1의 geometry/distance |
| **M2** | DES 엔진 (단일 설비 → 그룹 → 라우트) | 고장·배치 없는 기본 시뮬레이션 | 성능 측정, M/M/1 비교, SimPy 교차검증 |
| **M3** | 고장 + 배치 설비 + 반송기 | 완전한 DES | 가동률 수렴, 배치 동작 |
| **M4** | 지표 + 생산능력 탐색 + CLI | `fablayout simulate` 동작 | 해석적 정합성, 포화 거동 |
| **M5** | 기준선 + 대리지표 + 상관 검증 | 대리지표 신뢰성 확인 | **ρ ≥ 0.7 (게이트)** |
| **M6** | SA + 2단 파이프라인 + 병렬화 | `fablayout optimize` 동작 | 최적화 유효성 |
| **M7** | FastAPI + 배치도/대시보드 UI | 웹에서 시뮬레이션 실행 | 수동 확인 |
| **M8** | Before/After 비교 + 애니메이션 | UI 완성 | 수동 확인 |

**M5는 게이트다.** 대리지표가 DES와 상관이 없으면 2단 구조를 버리고 다른 접근(대리모델
학습, 또는 DES 직접 SA + 평가 예산 축소)으로 선회해야 한다. M6에 들어가기 전에 반드시
확인한다.
